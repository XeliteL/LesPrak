# 2. Объектно-ориентированная реализация на языке Java

> Черновик. Код: `src/java/`. Сборка и тесты: `cd src/java && mvn package` (Maven встроен в IntelliJ IDEA), демонстрация: `java -jar target/realty-1.0.jar`, замеры: `java -cp target/classes realty.Bench`.

## 2.1. Средства реализации

Реализация выполнена в среде разработки IntelliJ IDEA. Проект собирается системой сборки Maven, его описание хранится в файле `pom.xml`, поэтому IDE открывает проект без дополнительной настройки. Используемые инструменты приведены в Таблице 2.1.

| Инструмент | Версия | Назначение |
|---|---|---|
| OpenJDK | 27.0.1 (компиляция для Java 21) | компилятор и среда выполнения |
| Apache Maven | 3.9 | сборка, запуск тестов, упаковка в архив JAR |
| JUnit | 5.11 | модульное тестирование |

Код компилируется для Java 21 — версии с долгосрочной поддержкой. В ней уже есть все использованные возможности языка: записи, запечатанные интерфейсы и сопоставление с образцом в операторе `switch`. Поэтому программа запускается на любой среде выполнения Java начиная с версии 21. Основная программа не использует сторонних библиотек: даты обрабатываются пакетом `java.time`, коллекции — пакетом `java.util`. Для чтения исходных данных в формате JSON написан небольшой разборщик (класс `Json`), так как стандартная библиотека Java не содержит средств работы с JSON. Единственная внешняя зависимость — библиотека JUnit, она нужна только для тестов.

Программа читает тот же файл исходных данных, что и процедурная реализация. Класс `DataLoader` проверяет наличие обязательных полей и сообщает обо всех найденных ошибках, а затем создаёт объекты предметной области. Строковые коды статусов и условий преобразуются в значения перечислений. Неизвестный код приводит к ошибке при загрузке, а не при работе алгоритма.

## 2.2. Демонстрация работы

Класс `Main` выполняет те же действия, что и программа `main.py` процедурной реализации: оценивает квартиру, подбирает объекты под две заявки, проверяет сделку в работе и рассчитывает комиссию за октябрь 2026 года. Алгоритмы собираются статическими фабричными методами с параметрами по умолчанию:

```
ValuationResult result = ComparativeValuator.standard(data.listings()).estimate(subject, TODAY);
switch (result) {
    case ValuationResult.Insufficient r -> System.out.println("Недостаточно аналогов: найдено " + r.analogsFound());
    case ValuationResult.Estimate r -> System.out.println("Рекомендуемая цена: " + format(r.price()));
}
List<Match> matches = ObjectMatcher.standard().match(request, data.objects(), 5);
DealReport report = DealInspector.standard(data.docTypes()).inspect(deal, TODAY);
MonthlyReport month = CommissionCalculator.standard().monthly(data.deals(), YearMonth.of(2026, 10));
```

На условных данных вывод программы совпадает с выводом процедурной реализации, приведённым в материалах аналитического этапа: рекомендуемая цена квартиры 20 530 000 руб., одинаковые наборы и порядок подобранных объектов, одинаковые замечания по сделке 6 и комиссия агентства за месяц 1 354 000 руб. Совпадение проверяется автоматически сквозным тестом (раздел 2.3).

Чтобы результаты совпадали до рубля, при переносе алгоритмов учтены различия языков. Функция `round` в Python округляет половину до ближайшего чётного числа, поэтому в Java вместо `Math.round`, который округляет половину вверх, используется `Math.rint`. Оценка соответствия в алгоритме 2 округляется до десятых через `BigDecimal` с режимом `HALF_EVEN`. Арифметические операции выполняются в том же порядке, что и в процедурной реализации.

## 2.3. Тестирование

Модульные тесты написаны на JUnit 5 и повторяют тесты процедурной реализации на тех же исходных данных и с теми же ожидаемыми результатами. Добавлены тесты, которые проверяют свойства объектно-ориентированной реализации: проверку допустимости значений в конструкторах, подключение новой корректировки и нового условия без изменения классов алгоритмов, а также совпадение вывода программы с эталонным выводом процедурной реализации. Состав тестов приведён в Таблице 2.2.

| Класс тестов | Что проверяется | Число тестов |
|---|---|---|
| `ModelTest` | определение категории этажа; отказ конструкторов создавать квартиру с некорректными характеристиками | 2 |
| `DataLoaderTest` | разбор JSON и отказ на некорректном тексте; сообщение об отсутствующем поле; загрузка демонстрационных данных | 3 |
| `ValuationTest` | отбор аналогов по каждому условию; поправка на этаж; оценка по одинаковым аналогам; исключение выброса; недостаточное число аналогов; пустой список предложений; подключение дополнительной корректировки лямбда-выражением | 7 |
| `MatchingTest` | жёсткие условия заявки; ранжирование и ограничение числа результатов; отсутствие подходящих объектов; подключение нового условия | 4 |
| `DocumentsTest` | зависимость перечня документов от условий сделки; выбор последнего документа; готовность сделки; отсутствующие, просроченные и истекающие документы; порог 115-ФЗ и просроченные этапы | 5 |
| `CommissionTest` | минимальная комиссия; расчёт по ступеням шкалы и независимость от разбиения на сделки; проверка корректности шкалы; отчёт за месяц | 4 |

Все 26 тестов выполняются успешно. Тесты запускаются при каждой сборке проекта командой `mvn package`, и при ошибке в тестах архив программы не собирается.

## 2.4. Время работы

Время работы алгоритмов измерено программой `Bench` по той же методике, что и для процедурной реализации: синтетические данные объёмом от 1 000 до 1 000 000 записей, медиана нескольких запусков, процессор Intel Core i7-13700H. В отличие от интерпретатора Python, виртуальная машина Java компилирует часто выполняемый код в машинный код во время работы программы (JIT-компиляция). Поэтому перед замером каждый алгоритм выполняется в течение 0,5 с для прогрева, а затем берётся медиана 11 запусков. Результаты приведены в Таблице 2.3.

| Объём данных n | Алгоритм 1, мс | Алгоритм 2, мс | Алгоритм 3, мс | Алгоритм 4, мс |
|---|---|---|---|---|
| 1 000 | 0,03 | 0,05 | 0,02 | 1,05 |
| 10 000 | 0,09 | 0,93 | 0,24 | 3,23 |
| 100 000 | 2,32 | 6,87 | 3,97 | 40,30 |
| 1 000 000 | 34,61 | 74,15 | 57,58 | 750,94 |

При переходе от 100 000 к 1 000 000 записей время работы алгоритмов 1–3 возрастает в 11–15 раз, то есть близко к линейной зависимости. Превышение над десятикратным ростом объясняется тем, что миллион объектов не помещается в кэш процессора и время доступа к памяти растёт. Время алгоритма 4 возрастает в 19 раз, что согласуется с оценкой O(m log m) за счёт сортировки, полученной на аналитическом этапе. На малых объёмах (1 000 и 10 000 записей) время измеряется десятыми и сотыми долями миллисекунды. Здесь сильнее влияют кэш процессора и сборка мусора, поэтому рост времени не пропорционален n. Повторные запуски дают разброс результатов до 30–50 %, поэтому значения следует рассматривать как оценку порядка величины.
