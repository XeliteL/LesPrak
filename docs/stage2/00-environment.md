## 0.1. Состав инструментального окружения

Работа над практикой ведётся в ОС Linux (дистрибутив Arch Linux). Состав окружения выбран по стеку технологий, указанному в задании на практику.

| Инструмент | Версия | Назначение |
|---|---|---|
| WebStorm (JetBrains) | через JetBrains Toolbox | IDE для фронтенда: разработка на TypeScript/React, работа с git, запуск тестов |
| VSCodium (открытая сборка Visual Studio Code) | 1.121 | редактор для серверной части на Go и для материалов практики (Markdown, диаграммы) |
| Node.js | 22.23.3 | среда выполнения для сборки фронтенда и запуска инструментов (npm) |
| Go | 1.27.1 | язык разработки серверной части (микросервисы) |
| Docker | 29.8.1 | контейнеризация сервисов |
| Git | 2.55.0 | система контроля версий |
| GitHub, GitHub CLI (`gh`) | — | удалённое хранение репозиториев, pull request, управление репозиториями из терминала |
| draw.io | — | построение диаграмм (UML, ER, BPMN) |

Работа распределена между двумя средами. WebStorm используется для фронтенда: он поддерживает TypeScript, React и SCSS без дополнительной настройки. VSCodium используется для серверной части на Go (через расширение для Go) и для работы с текстами отчёта. VSCodium — это сборка Visual Studio Code из открытого исходного кода без телеметрии и фирменных компонентов Microsoft, по функциональности и поддержке расширений он совпадает с VS Code.

В проекте SoulMe настроены инструменты контроля качества кода, WebStorm поддерживает их встроенно:
- **ESLint** с правилами typescript-eslint: статический анализ TypeScript-кода, в том числе контроль порядка импортов;

## 0.2. Организация работы с системой контроля версий

В рамках практики используются два git-репозитория на GitHub.

1. **SoulMe** (https://github.com/XeliteL/SoulMe, публичный, лицензия MIT) — исходный код прототипа стримингового сервиса.
2. **LesPrak** (приватный) — материалы практики: тексты отчёта по этапам, диаграммы, учебные реализации алгоритмов.

Такое разделение отделяет код продукта от учебной документации: у них разный жизненный цикл, и в открытый репозиторий не попадают служебные материалы практики.

### Модель ветвления

В репозитории SoulMe используется упрощённая модель feature-веток (feature branch workflow) [36]:
- `main` — стабильная ветка, изменения попадают в неё только через pull request;
- `feature/front` — разработка клиентской части;
- `feature/back` — ветка, созданная для разработки серверной части.

Изменения из feature-ветки вливаются в `main` через pull request. К моменту написания отчёта в репозитории слиты 4 pull request. Для pull request подготовлен шаблон с описанием изменений, типом изменения и чек-листом: проверки `npm run check` проходят, изменения разбиты на логически цельные коммиты.

### Соглашение о коммитах

Сообщения коммитов оформляются по спецификации Conventional Commits [35]: в начале сообщения указывается тип изменения. В истории SoulMe 77 коммитов, распределение по типам такое:

| Тип | Назначение | Количество |
|---|---|---|
| `feat` | новая функциональность | 27 |
| `fix` | исправление ошибки | 11 |
| `style` | визуальные изменения | 8 |
| `content` | изменение текстового содержимого | 7 |
| `refactor` | рефакторинг без изменения поведения | 6 |
| `test` | тесты | 5 |
| `chore` | служебные изменения (настройка проекта) | 5 |
| `docs` | документация | 4 |
| `perf` | оптимизация производительности | 1 |

Благодаря единому формату историю изменений легко читать и фильтровать по типам.

### Сопроводительные файлы репозитория

Кроме исходного кода, репозиторий SoulMe содержит стандартные файлы открытого проекта:
- `README.md` — описание проекта, стека, команд и структуры каталогов;
- `LICENSE` — лицензия MIT;
- `CONTRIBUTING.md` — правила участия в проекте;
- `SECURITY.md` — порядок сообщения об уязвимостях;
- шаблоны issue (сообщение об ошибке, предложение функции) и шаблон pull request.

## 0.3. Выводы

В ходе этапа освоено инструментальное окружение для разработки клиент-серверного приложения: IDE WebStorm и редактор VSCodium, средства контроля качества кода, а также Go и Docker для будущей серверной части. Работа с системой контроля версий Git [37] построена на feature-ветках, pull request и соглашении Conventional Commits. Код продукта и материалы практики хранятся в двух отдельных репозиториях на GitHub. Созданная ветка `feature/back` станет основой для разработки серверной части MVP на следующих этапах.
